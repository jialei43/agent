# Agent 五种核心思想：原理与企业级实现

## 概览

| 思想 | 核心问题 | 适用场景 | 文件 |
|---|---|---|---|
| ReAct | 如何边思考边行动？ | 需要多工具协作的复杂查询 | 01_react_agent.py |
| Plan-and-Execute | 如何分离规划与执行？ | 多步骤、有依赖关系的任务 | 02_plan_execute_agent.py |
| Reflection | 如何保证输出质量？ | 高质量内容生成、关键决策 | 03_reflection_agent.py |
| Multi-Agent | 如何分工协作？ | 复杂业务路由、专家系统 | 04_multi_agent.py |
| Memory-Augmented | 如何利用历史经验？ | 持续学习、个性化服务 | 05_memory_agent.py |

## 一、ReAct（Reasoning + Acting）

### 原理

ReAct 的核心是把"推理"和"行动"交织在一个循环中：

```
用户问题
  ↓
Thought：分析当前情况，决定下一步做什么
  ↓
Action：选择工具 + 填入参数
  ↓
Observation：工具返回结果
  ↓
Thought：根据结果继续推理（是否需要更多信息？是否可以回答？）
  ↓ （循环直到可以给出最终答案）
Final Answer
```

本质上是让 LLM 生成带格式的 Chain-of-Thought，格式为：
```
Thought: ...
Action: tool_name
Action Input: {...}
Observation: ...（框架填入工具结果）
Thought: ...
Final Answer: ...
```

### 与普通 Function Call 的区别

| | Function Call | ReAct |
|---|---|---|
| 推理过程 | 隐式（LLM 内部） | 显式（每步都有 Thought） |
| 工具调用次数 | 通常单次 | 多轮，按需决定 |
| 可解释性 | 低 | 高（可以看到每步思考） |
| 适合场景 | 明确的单工具任务 | 需要探索的复杂任务 |

### 企业级实现思路

1. **工具设计**：工具粒度要细，单一职责，描述要精准（LLM 靠描述选工具）
2. **Prompt 工程**：System prompt 注入业务约束、角色定义、输出格式
3. **循环保护**：设置 `max_iterations` 防止死循环，设置 `max_execution_time` 防止超时
4. **观察结果截断**：工具返回结果太长时截断，避免 context 溢出
5. **错误恢复**：工具调用失败时让 Agent 知晓并换策略，而非直接抛异常

### create_react_agent vs create_tool_calling_agent

业务开发中，`create_tool_calling_agent` 是更常见的选择，两者本质区别在于工具调用机制：

| 对比项 | `create_react_agent` | `create_tool_calling_agent` |
|---|---|---|
| 工具调用机制 | 解析 LLM 输出的文本（`Action: xxx`） | 模型原生 Function Calling（JSON schema） |
| 稳定性 | 容易格式解析失败 | 结构稳定，不依赖文本格式 |
| 提示词要求 | 必须写 `{tools}` `{tool_names}` 占位符 | 不需要，框架自动注入工具 schema |
| 对模型要求 | 任意模型可用 | 需要模型支持 tool calling |
| 调试难度 | 高（文本解析错误难定位） | 低（结构化报错） |
| 推理过程 | 显式（每步 Thought 写在文本里） | 隐式（LLM 内部推理） |

**`create_react_agent` 适用场景：**
- 模型不支持 Function Calling（老模型、部分开源模型）
- 需要推理过程可见可审计（Thought 链写进上下文）
- 教学/演示推理思想

**`create_tool_calling_agent` 业务写法：**

```python
from langchain.agents import create_tool_calling_agent, AgentExecutor
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是专业代码审查助手"),
    ("human", "{input}"),
    ("placeholder", "{agent_scratchpad}"),  # 不需要 {tools} {tool_names}
])

agent = create_tool_calling_agent(llm, tools, prompt)
executor = AgentExecutor(agent=agent, tools=tools)
```

> 现代主流模型（OpenAI、Claude、Qwen 等）均支持 Function Calling，业务开发优先使用 `create_tool_calling_agent`，稳定性和可维护性更好。

### 企业级落地：执行记录存储 + 流式输出

#### 1. 为什么 Tool Calling + think 工具更适合存数据库

两种方案的 `intermediate_steps` 结构完全不同：

**ReAct** — 推理藏在非结构化文本里，需正则提取：
```python
# action.log 是一整段混合文本
AgentAction(
    tool='check_security_issues',
    tool_input='import pickle...',
    log='Thought: 代码里有 pickle，需要检查安全\nAction: check_security_issues\nAction Input: ...'
)
# 要提取 Thought 必须：
thought = re.search(r'Thought:(.*?)(?=Action:|$)', action.log, re.DOTALL)
```

**Tool Calling + think** — 每步都是结构化 dict，直接序列化：
```python
# think 调用 → 推理结构化
ToolAgentAction(tool='think',       tool_input={'reasoning': '代码里有 pickle，需要检查安全漏洞'})
# 工具调用 → 入参结构化
ToolAgentAction(tool='check_security_issues', tool_input={'code': 'import pickle...'})
```

存库对比：

| 字段 | ReAct | Tool Calling + think |
|---|---|---|
| 推理内容 | 正则从 `log` 提取 | `tool_input['reasoning']` 直取 |
| 工具入参 | 字符串，需解析 | dict，直接 JSON 序列化 |
| 并发步骤 | 不支持 | 可记录哪些步骤并行执行 |

存库代码示例：
```python
def save_execution_to_db(db, task_id: str, result: dict):
    steps = []
    for i, (action, observation) in enumerate(result["intermediate_steps"]):
        steps.append({
            "task_id": task_id,
            "step_index": i,
            "type": "thought" if action.tool == "think" else "action",
            "tool": action.tool,
            "input": action.tool_input,   # 直接是 dict，无需解析
            "output": str(observation),
        })
    db.insert_many("execution_steps", steps)
```

#### 2. 解决用户等待问题：astream_events 流式输出

`invoke` 等全部执行完再返回，用户需要等待整个 Agent 跑完。
`astream_events` 每一步执行完立刻推送事件，前端可实时展示进度。

```python
async def stream_review(agent_executor, code: str):
    async for event in agent_executor.astream_events(
        {"input": f"审查以下代码：\n{code}"},
        version="v2",
    ):
        kind = event["event"]

        if kind == "on_tool_start":
            tool_name = event["name"]
            labels = {
                "think":                  "思考中...",
                "check_security_issues":  "正在扫描安全漏洞...",
                "analyze_complexity":     "正在分析代码复杂度...",
                "check_code_style":       "正在检查代码规范...",
                "check_test_coverage_hints": "正在分析测试覆盖...",
            }
            yield f"\n⚙️  {labels.get(tool_name, tool_name)}"

        elif kind == "on_tool_end":
            yield "✅ 完成"

        elif kind == "on_chat_model_stream":
            # Final Answer 也逐字流式输出，不等全部生成完
            chunk = event["data"]["chunk"].content
            if chunk:
                yield chunk
```

#### 3. 解决输出不友好问题：Callback 层格式化

Tool Calling 的结构化数据反而是优势——你完全控制展示措辞，不受 LLM 生成文本影响：

```python
def on_tool_start(self, serialized, input_str, **_):
    tool_name = serialized.get("name")
    labels = {
        "think":                  "思考中...",
        "check_security_issues":  "正在扫描安全漏洞...",
        "analyze_complexity":     "正在分析代码复杂度...",
    }
    print(f"⚙️  {labels.get(tool_name, tool_name)}")
```

ReAct 的"推理过程自然可读"是 LLM 生成的文本，无法控制措辞；
Tool Calling 拿到的是结构化数据，展示、存储、告警均可按需定制。

#### 4. 整体架构分层

```
用户界面层    ← astream_events 流式推送 + Callback 格式化为友好文案
     ↓
Agent 执行层  ← Tool Calling + think（结构化、可靠）
     ↓
持久化层      ← intermediate_steps 存数据库（结构化 JSON，无需解析）
```

同一次执行，流式展示给用户 和 结构化存库 在各自层处理，互不干扰。

## 二、Plan-and-Execute（规划-执行分离）

### 原理

将任务拆分为两个明确阶段：

```
用户任务
  ↓
【规划阶段】Planner LLM
  分析任务 → 生成结构化执行计划（步骤列表）
  输出：[Step1, Step2, Step3, ...]
  ↓
【执行阶段】Executor LLM（循环）
  取出 Step1 → 执行（可调用工具）→ 记录结果
  取出 Step2 → 执行 → 记录结果
  ...
  ↓
【汇总阶段】
  所有步骤结果 → 综合回答
```

可选增强：**Re-planning**（执行失败或发现新信息时重新规划）

### 与 ReAct 的区别

| | ReAct | Plan-and-Execute |
|---|---|---|
| 规划时机 | 每步临时决定 | 开始时整体规划 |
| 全局视野 | 弱（只看当前） | 强（看到全局步骤） |
| 灵活性 | 高（随时调整） | 低（计划一旦定难改） |
| 适合任务 | 探索性任务 | 结构化、已知流程的任务 |

### 企业级实现思路

1. **计划结构化**：用 Pydantic 模型约束计划格式，防止 LLM 生成格式不一致的计划
2. **步骤依赖管理**：步骤间有依赖时，传递前一步结果给下一步
3. **Re-planning 触发条件**：执行失败 / 发现计划中未考虑的情况 / 用户中途修改需求
4. **并行执行**：无依赖的步骤可并行执行，提升效率
5. **审批门控**：关键步骤执行前插入人工审批节点（Human-in-the-loop）

## 三、Reflection（反思-自我优化）

### 原理

Agent 生成初稿后，用一个 Critic 视角评估输出质量，根据评估反馈迭代改进：

```
用户需求
  ↓
【生成阶段】Generator
  生成初稿
  ↓
【评估阶段】Critic（可以是同一个 LLM，也可以是独立 LLM）
  按评分维度打分 + 指出问题
  ↓
  分数 >= 阈值？
    是 → 输出最终结果
    否 → 生成修改建议
  ↓
【修订阶段】Generator
  根据修改建议重新生成
  ↓（循环，设置最大迭代次数）
```

### 核心价值

- 解决 LLM 单次生成质量不稳定的问题
- 可以定义领域特定的质量标准（不同于通用 LLM 的泛化偏好）
- 适合对准确性、合规性要求高的场景

### 企业级实现思路

1. **评分维度设计**：针对业务场景定义维度（如：合规性、完整性、可执行性、风险提示）
2. **阈值策略**：不同场景用不同阈值，高风险场景（法律、财务）阈值更高
3. **Critic 独立性**：Critic 和 Generator 最好使用不同的 temperature 甚至不同模型
4. **修改建议结构化**：Critic 输出结构化建议（而非自由文本），便于 Generator 针对性修改
5. **收敛检测**：多次迭代分数不再提升时提前终止，避免无效循环

## 四、Multi-Agent（多智能体协作）

### 原理

多个专业化 Agent 各司其职，由一个协调者（Supervisor）分配任务：

```
用户请求
  ↓
【Supervisor】
  意图分类 → 路由到对应 Agent
  ↓
┌─────────┬─────────┬─────────┐
│Agent A  │Agent B  │Agent C  │
│（专家1）│（专家2）│（专家3）│
└────┬────┴────┬────┴────┬────┘
     └─────────┼─────────┘
               ↓
【Aggregator】（可选）
  汇总多个 Agent 的结果
  ↓
最终回答
```

常见拓扑：
- **分层路由**：Supervisor → 专家 Agent（最常用）
- **流水线**：Agent A → Agent B → Agent C（顺序处理）
- **辩论模式**：多个 Agent 各自给出答案 → 投票或综合

### 企业级实现思路

1. **职责边界清晰**：每个 Agent 的职责范围要明确，避免重叠导致路由混乱
2. **Supervisor 轻量化**：Supervisor 只做路由，不做业务处理，保持响应快
3. **Agent 间通信格式**：定义统一的消息格式（Pydantic），防止 Agent 间信息丢失
4. **失败降级**：专家 Agent 失败时，Supervisor 有降级策略（换 Agent / 直接回答 / 人工介入）
5. **状态追踪**：记录每个 Agent 的执行状态，支持断点续跑和问题定位

## 五、Memory-Augmented（记忆增强）

### 原理

Agent 拥有多层记忆，使其能利用历史经验：

```
用户输入
  ↓
【记忆检索】
  短期记忆（当前会话对话历史）
  长期记忆（向量检索：相似历史案例）
  用户画像（偏好、角色、历史偏好）
  ↓
【上下文组装】
  系统 Prompt + 用户画像 + 相关历史 + 当前对话
  ↓
LLM 推理 + 工具调用
  ↓
【记忆更新】
  将本次对话存入长期记忆
  更新用户画像
  ↓
输出
```

### 记忆类型

| 类型 | 内容 | 存储方式 | 生命周期 |
|---|---|---|---|
| 短期记忆 | 当前会话消息历史 | 内存列表 | 会话结束清空 |
| 情节记忆 | 过去的 Q&A 对、任务执行记录 | 向量数据库 | 持久化 |
| 语义记忆 | 领域知识、业务规则 | 向量数据库 | 人工维护 |
| 用户画像 | 偏好、角色、习惯 | KV 存储 | 长期更新 |

### 企业级实现思路

1. **记忆分层存储**：热数据（近期）放内存，冷数据放向量库，降低检索延迟
2. **相关性过滤**：检索长期记忆时，设置相似度阈值，避免引入无关噪音
3. **记忆老化机制**：时间越久的记忆权重越低，防止过时信息影响决策
4. **隐私隔离**：多用户场景下，用户记忆严格隔离，防止信息泄露
5. **记忆压缩**：对话历史过长时，用 LLM 摘要压缩，保留关键信息

## 六、五种思想的选型参考

```
任务是否有明确的执行步骤？
  是 → Plan-and-Execute
  否 ↓

是否需要多次工具调用、推理过程可见？
  是 → ReAct
  否 ↓

是否对输出质量有高要求，需要多轮自校验？
  是 → Reflection
  否 ↓

是否涉及多个专业领域，需要专家分工？
  是 → Multi-Agent
  否 ↓

是否需要利用历史经验、个性化响应？
  是 → Memory-Augmented
  否 → 普通 Function Call 即可
```

实际系统中通常组合使用：
- **ReAct + Memory**：有记忆的探索型 Agent
- **Plan-Execute + Reflection**：高质量多步骤任务
- **Multi-Agent + Memory**：大规模企业级 AI 系统
