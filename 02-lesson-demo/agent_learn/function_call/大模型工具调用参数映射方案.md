# 大模型工具调用参数映射方案

> 解决问题：用户自然语言输入（"帮我定今天北京到上海的机票"）如何可靠地映射到函数参数

---

## 一、核心机制

LLM Function Calling 的本质是：**模型读取 Schema 的 `description` 字段 + 用户输入，输出填好参数的 JSON**。

```
用户说："帮我定今天北京到上海的机票"
                    ↓
LLM 读取 FlightSearchInput 的 Field(description)：
  origin:      "出发城市，例如：北京、上海"
  destination: "目的城市，例如：上海、广州"
  date:        "出发日期，格式 YYYY-MM-DD"
                    ↓
LLM 输出：{"origin": "北京", "destination": "上海", "date": "???"}
```

**"今天" 无法映射** —— 因为 LLM 不知道当前日期，除非主动注入。这是生产环境的第一个核心问题。

---

## 二、常见失败场景

| 场景 | 用户输入示例 | 问题根因 |
|---|---|---|
| 动态时间 | "今天"、"明天"、"下周五" | LLM 训练时不知道当前日期 |
| 缺失必填参数 | 没说目的地、没说乘客数 | 模型到底是猜还是问？ |
| 城市别名 | "魔都"、"帝都"、"羊城" | 训练数据覆盖不均，不可靠 |
| 机场代码 | "PEK"、"PVG"、"SHA" | 同一城市多个代码需要归一化 |
| 参数越界 | "订10个人的票" | 超出 `passengers ≤ 9` 的业务限制 |
| 格式不合规 | "2026/06/01"（斜线） | 应为 YYYY-MM-DD（横线） |

---

## 三、企业级四层防护方案

```
用户输入
   │
   ├─ Layer 2：实体预处理（别名 → 标准名，进 LLM 之前）
   │
   ├─ Layer 1：注入 System Prompt（当前日期 / 用户偏好）
   │
   ▼
  LLM（读 Pydantic Field description 做参数映射）
   │
   ├─ 参数不全 → Layer 3：Slot Filling 追问 → 用户补充 → 重新推理
   │
   ├─ 参数有误 → Layer 4：Pydantic 校验错误反馈 → LLM 自修正 → 重试（最多2次）
   │
   └─ 参数齐全合法 → 执行工具函数 → 返回结果
```

---

### Layer 1 — System Prompt 上下文注入

**解决问题**：动态时间（今天/明天/后天）、用户默认偏好

**原理**：LLM 不知道"今天"是哪天，是**信息缺失**问题而非能力问题。把运行时信息写入 system prompt，模型就有依据做推算。

```python
def build_system_prompt(user_id: str) -> str:
    now = datetime.now()
    tomorrow = (now + timedelta(days=1)).strftime("%Y-%m-%d")
    profile = get_user_profile(user_id)  # 从 DB/Redis 读取用户偏好

    return f"""
【当前时间上下文】
- 今天日期：{now.strftime("%Y-%m-%d")}（{weekday_cn}）
- 明天日期：{tomorrow}

【当前用户信息】
- 默认乘客数：{profile['default_passengers']}
- 偏好舱位：{profile['preferred_cabin']}

【参数映射规则】
- 用户说"今天" → 日期填 {now.strftime("%Y-%m-%d")}
- 用户没有指定乘客数 → 使用用户默认乘客数
- 缺少必填参数时，直接追问用户，不要猜测
"""
```

**注入内容清单**：

| 注入内容 | 来源 | 解决的问题 |
|---|---|---|
| 当前日期/星期 | `datetime.now()` | 今天/明天/后天 |
| 用户默认乘客数 | 用户数据库 | 未提及乘客数时的默认值 |
| 用户偏好舱位 | 用户数据库 | 未提及舱位时的默认值 |
| 用户历史偏好城市 | 行为日志 | 减少追问次数 |

### Layer 2 — 实体预处理（进 LLM 之前）

**解决问题**：城市别名、机场代码、非标准表达

**原理**：在进入 LLM 之前做字符串替换，**不依赖模型能力**，速度快、可控、可测试。

```python
CITY_ALIAS_MAP = {
    "魔都": "上海",   # 别名
    "帝都": "北京",
    "羊城": "广州",
    "PEK":  "北京",   # IATA 机场代码
    "SHA":  "上海",
    "PVG":  "上海",   # 浦东/虹桥都归一化到城市
}

def normalize_query(query: str) -> str:
    for alias, standard in CITY_ALIAS_MAP.items():
        query = query.replace(alias, standard)
    return query
```

**生产环境升级路径**：

```
简单字典替换（当前方案）
        ↓
专有 NER 模型（HanLP / BERT-NER）
        ↓
知识图谱（实体链接，处理歧义）
```

---

### Layer 3 — Slot Filling 多轮追问

**解决问题**：用户输入不完整，缺少必填参数

**原理**：LLM 在 `Field(description)` 的指导下，发现必填参数缺失时主动向用户追问，而不是随意猜测。

```
用户："帮我定明天从北京出发的机票"
                ↓
LLM 判断 destination 缺失，输出自然语言：
"请问您要飞往哪个城市？"
                ↓
用户："上海"
                ↓
LLM 补齐参数 → 调用工具
```

**关键：在 Field description 中给 LLM 明确指令**：

```python
class FlightSearchInput(BaseModel):
    destination: str = Field(
        # 告诉 LLM：缺这个参数时要追问，不能猜
        description="目的城市。必填，如果用户未提及，请追问用户目的地"
    )
    passengers: int = Field(
        default=1,
        # 告诉 LLM：缺这个参数时用默认值，不需要追问
        description="乘客人数 1-9。用户未提及时使用 system prompt 中的用户默认乘客数"
    )
```

**追问 vs 使用默认值的决策规则**：

| 参数类型 | 策略 | 说明 |
|---|---|---|
| 必填且无默认（origin/destination） | 追问 | 无法合理猜测 |
| 有默认值（passengers/cabin_class） | 用 system prompt 中的用户偏好 | 减少摩擦 |
| 有强业务约束（date 不能是过去） | 追问 + 说明原因 | "该日期已过，请重新选择" |

### Layer 4 — Pydantic 校验 + 错误反馈重试

**解决问题**：LLM 填了非法参数值（格式错误、越界、枚举外的值）

**原理**：`StructuredTool.invoke()` 触发 Pydantic 校验，校验失败时把错误信息反馈给 LLM，让它自我修正，最多重试 2 次防止死循环。

```python
MAX_RETRY = 2  # 最多重试次数，防止死循环

retry_count = 0
while retry_count <= MAX_RETRY:
    try:
        result = tool_obj.invoke(tc["args"])  # Pydantic 自动校验
        break  # 成功，退出重试
    except Exception as e:
        retry_count += 1
        # 把错误原因反馈给 LLM，触发自我修正
        messages.append(HumanMessage(
            content=f"工具调用失败：{str(e)}，请修正参数后重新调用"
        ))
        retry_response = llm_with_tools.invoke(messages)  # LLM 重新生成参数
        tc = retry_response.tool_calls[0]  # 取修正后的参数
```

**校验失败场景示例**：

```
LLM 填了 passengers=15
    ↓
Pydantic: ValidationError: passengers 最大值为 9，收到 15
    ↓
反馈给 LLM："参数错误：passengers 不能超过 9，请修正"
    ↓
LLM 自修正：passengers=9
    ↓
校验通过，执行工具
```

## 四、Schema 设计最佳实践

Schema 的 `description` 字段是 LLM 做参数映射的**唯一依据**，写得越精确，映射越准确。

### 好的 description vs 差的 description

```python
# 差：信息量不足，LLM 不知道如何填
date: str = Field(description="日期")

# 好：格式、来源、推算规则都明确
date: str = Field(
    description="出发日期，格式 YYYY-MM-DD（横线分隔）。"
                "根据 system prompt 中今天/明天的日期推算，"
                "不要使用相对表述，必须填具体日期"
)
```

```python
# 差：枚举值不明确
cabin_class: str = Field(description="舱位")

# 好：枚举值 + 默认策略
cabin_class: str = Field(
    description="舱位：economy（经济舱）、business（商务舱）、first（头等舱）。"
                "用户未提及时使用 system prompt 中的用户偏好舱位"
)
```

### 加约束条件减少校验失败

```python
passengers: int = Field(
    default=1,
    ge=1,   # 最少 1 人（Pydantic 自动校验）
    le=9,   # 最多 9 人（航空公司限制）
    description="乘客人数 1-9"
)
```

## 五、各层方案对比

| 层 | 解决问题 | 实现位置 | 依赖 LLM 能力 |
|---|---|---|---|
| Layer 1 上下文注入 | 动态日期/用户偏好 | System Prompt | 否（注入静态信息） |
| Layer 2 实体预处理 | 城市别名/机场代码 | LLM 调用之前 | 否（字典/NER） |
| Layer 3 Slot Filling | 缺失必填参数 | 多轮对话循环 | 是（LLM 主动追问） |
| Layer 4 校验重试 | 非法参数值 | 工具执行层 | 是（LLM 自修正） |
